# BOT_INFO — что умеет бот и какие права ему нужны

Документ описывает **текущее** состояние бота (не планы). Основан на коде в этом репозитории.

- Стек: Java 21, JDA 6.5.0, PostgreSQL (драйвер 42.7.4) + HikariCP 5.1.0, Flyway 10.17.0, logback, dotenv-java, Jackson. Сборка: Gradle (wrapper 9.7.1).
- Точка входа: `com.pocketsage.tournament.Main` → `BotLauncher`.
- Версия: `1.0.0`.

---

## 1. Запуск и конфигурация

```
./gradlew run      # запуск бота
./gradlew test     # тесты
./gradlew build    # сборка + тесты + jar (build/libs/tournament-doto-1.0.0.jar)
```

Конфиг читается из **`.env`** в корне проекта; если `.env` нет — из шаблона **`env.env`** (`EnvLoader`).

| Ключ | Обязателен | Назначение |
|---|---|---|
| `DISCORD_TOKEN` | да | токен бота |
| `DATABASE_URL` | да | JDBC-строка, например `jdbc:postgresql://localhost:5432/tournament` |
| `DATABASE_LOGIN` | да | пользователь БД |
| `DATABASE_PASSWORD` | да | пароль БД |
| `OPENDOTA_APIKEY` | нет | ключ OpenDota для `/bind`; без него API работает, но с общим низким лимитом |

Порядок старта:

1. чтение конфига — при пустом обязательном ключе печатается
   `Не удалось запустить бота: Переменная X не задана в .env/env.env` и процесс завершается с кодом 1;
2. инициализация пула HikariCP (max 20 соединений, min idle 2, timeout 5 с, leak detection 60 с);
3. **Flyway-миграции** из `classpath:db/migration` (V1, V2, …);
4. вход в Discord (`JDABuilder`), статус «Dota 2 close», ожидание READY;
5. регистрация слэш-команд обработчиками.

При неверном токене: `Не удалось запустить бота: неверный DISCORD_TOKEN (The provided token is invalid!)`, код выхода 1.
По Ctrl+C срабатывает shutdown-hook: JDA гасится, пул соединений закрывается.

## 2. Слэш-команды

| Команда | Описание в Discord | Кто может | Что делает сейчас |
|---|---|---|---|
| `/bind` | Привязать Steam-аккаунт по Steam ID | любой участник | модалка с полем `Steam ID`; бот принимает `account_id`, SteamID64, `STEAM_0:Y:Z` или ссылку с числовым хвостом, разбирает его в `account_id` и ходит в OpenDota. Ответ эфемерно: «✅ Steam привязан: **…** 🎮 Профиль создан в базе / ♻️ Профиль обновлён», с MMR и рангом, если OpenDota их отдал |
| `/bind_old` | Привязать Steam name вручную | любой участник | прежний `/bind`: модалка «Привязка Steam (вручную)» с полем `Steam name` (2–64 символа). Заполняет только `steam_name`, без `steam_id`, `dota_account_id` и MMR |
| `/create_close_dota` | Создать клоз Dota 2 | только роль **Closemod** (проверяется при вызове и повторно при отправке модалки) | модалка `Immortal draft?` (Y/N), `Gamemode` (Captains Mode / All Pick), `Toxic mode` (Y/N) → создаёт категорию, каналы, права и два сообщения (раздел 3) |
| `/help` | Узнать о командах | любой | **заглушка** — команда есть, обработчика нет, бот не отвечает |
| `/info` | Показать информацию о вас | любой | **заглушка** — обработчика нет |
| `/create_close_cs` | Создать клоз CS | любой | **заглушка** — обработчика нет |

Мелочи, которые стоит знать:

- команды регистрируются как **глобальные** (`upsertCommand` без гильдии) — в клиенте Discord
  могут появиться не сразу (до ~часа);
- каждую команду регистрирует свой обработчик (`CommandRegistry` — `/help`, `/info`, `/create_close_cs`,
  `SteamBindHandler` — `/bind`, `SteamBindOldHandler` — `/bind_old`,
  `DotaCloseHandler` — `/create_close_dota`);
- в `DotaCloseHandler` имя роли сравнивается точно как `Closemod`, а в `DotaCloseService`
  и в кнопке отмены — без учёта регистра;
- при ошибке БД в `/bind` и `/bind_old` детали уходят в лог, а игроку показывается
  общее сообщение об ошибке;
- `/bind` ходит в OpenDota при каждом вызове, поэтому нужен доступ в интернет;
  `429` и «не найдено» отличаются от «сеть недоступна» разными ответами;
- у двух команд разные id модалок (`steam_bind_modal` и `steam_bind_old_modal`) —
  это их единственная связь в Discord, путать нельзя.

## 3. Клоз Dota 2: полный сценарий

### 3.1 Создание (после отправки модалки)

Создаётся категория `dota 2 close by <ник клозера>` (обрезается до 100 символов), внутри:

| Канал | Тип | Назначение |
|---|---|---|
| «чат-клоз» | текстовый | общий чат клоза (права по умолчанию) |
| «управление» | текстовый | панель клозера: информация + кнопки управления |
| «запись» | текстовый | карточка записи с кнопками записи |
| «команда-а» / «команда-б» | голосовой | войс команд на время матча |
| «ожидание» | голосовой | участники ждут здесь начала матча и возвращаются после него |

Затем настраиваются права (раздел 5) и отправляются **ровно два сообщения**:

1. **в «запись»** — карточка записи + кнопки 🟢 `Записаться` / 🔴 `Отписаться`;
2. **в «управление»** — основная информация + кнопки 🔵 `Создать матч` / 🟢 `Начать игру` /
   🔴 `Удалить матч` / 🔴 `Завершить матч` и 🔴 `Удалить клоз`.

Клозеру приходит эфемерный ответ «✅ Клоз создан: <категория>».

Карточка записи (пример, immortal draft = нет):

```
## Запись
**Игра:** Dota 2
**Режим:** Закрытый клоз
**Клозер:** <@111>
**Матч:** #1
**Immortal draft:** нет
**Gamemode:** All Pick
**Toxic:** да 🔥
**Мест занято:** 6/10
**Участники**

🟦 **Команда A** (2/5)
`1` <@222>
`2` <@333>
`3` Пусто
`4` Пусто
`5` Пусто

🟥 **Команда B** (1/5)
`6` <@444>
`7` Пусто
...
`10` Пусто
```

Номер слота — обычное число в кодовом блоке; при immortal draft идёт один
список из десяти слотов, без заголовков команд. Кастомные эмодзи вида
`<:1slot:ID>` не используются: они принадлежат чужому серверу, и игроки
видели бы их как сырое `:1slot:`.

Сообщение в «управление»:

```
🎮 **Клоз Dota 2**
Клозер: <@111>
Immortal draft: нет
Gamemode: All Pick
Toxic: да 🔥
Слотов: 10

📝 Запись — в канале #запись
```

### 3.2 Правила записи

- Всего **10 слотов** (`CloseRegistration.SLOTS`).
- **Immortal draft = да** → десять мест одним списком (команды соберут капитаны).
- **Immortal draft = нет** → «🟦 Команда A» (слоты 1–5) и «🟥 Команда B» (6–10), заполняются
  **по порядку записи** (первый записавшийся попадает в слот 1 и т. д.).
- Ники вставляются как `<@id>` — это и есть синяя подсветка-упоминание внутри Discord.
- Кнопка `Записаться` **блокируется**, когда все 10 мест заняты; `Отписаться` доступна всегда.
- После успешного нажатия сообщение перерисовывается на месте (новые сообщения не плодятся).
- Отказы приходят **эфемерно** (видит только нажавший): «⚠️ Вы уже записаны в этот клоз.»,
  «❌ Все 10 мест заняты.», «⚠️ Вы не записаны в этот клоз.»
- Если клоз уже неактивен (после отмены или после перезапуска бота):
  «❌ Этот клоз больше не активен.»

### 3.3 Проверка готовности (кнопка в «управлении»)

1. Бот пишет **в «запись»** сообщение с кнопкой `Я готов`:

```
⏱️ **Проверка готовности**
Клозер: <@111>
Нажмите «Я готов» до <t:1800000000:R> — кто не нажмёт, автоматически выпишется из клоза.

✅ Подтвердили (2): <@222>, <@333>
⏳ Ждём (2): <@444>, <@555>
```

`<t:...:R>` — нативный Discord-таймштамп: живой отсчёт («осталось 2 минуты») рисует сам клиент Discord.
2. Окно проверки — **3 минуты** (`CloseReadinessCheck.WINDOW`).
3. По истечении окна автоматически, без участия человека:
   - не подтвердившие **выписываются** из клоза;
   - сообщение проверки превращается в итог (кнопка снимается):
     «⏱️ Проверка готовности завершена / Выписаны за неявку: …» либо
     «✅ Проверка готовности завершена / Все подтвердили — никто не выписан.»;
   - карточка записи в «запись» перерисовывается: освободившиеся слоты снова «— свободно —»,
     а если клоз был полон — кнопка `Записаться` разблокируется.
4. Повторный запуск проверки: подтверждения сбрасываются, прежний таймер отменяется (никого не выпишет
   раньше времени). Клик по старому сообщению проверки тоже засчитывается, а актуальное сообщение
   синхронизируется.
5. Кто может подтверждать: только записанный игрок. Повторный клик — «⚠️ Вы уже подтвердили готовность.»,
   если проверка не запущена — «⚠️ Проверка готовности сейчас не запущена.»,
   если не записан — «⚠️ Вы не записаны в этот клоз.»

### 3.4 Старт игры и голосовые каналы

Голосовые каналы клоза: `команда-а`, `команда-б` и `ожидание` (создаются вместе с клозом).

1. Игрок нажал `Записаться` → бот **сразу переводит его в голосовой «ожидание»**.
2. Клозер нажал `Начать игру`:
   - **обычный матч** — состав уже разложен по командам, старт идёт сразу;
   - **immortal draft** — клозеру приходит кнопка `Состав команды A`. В модалке пять
     селектов по слоту; в вариантах — **ник** игрока (не id). Команду B клозер
     не выбирает: она автоматически добирается из оставшихся пяти игроков.
3. Старт матча: бот подменяет ники участников на Steam-ники (`/bind`) и переводит
   их в `команда-а` / `команда-б`.
4. `Завершить матч` или `Удалить матч`: ники возвращаются, все участники
   переводятся обратно в `ожидание`.

Если канал `ожидание` не найден (например, клоз создан до этой версии), бот пишет
в лог предупреждение и просто не переводит игроков — запись и старт матча
при этом работают.

### 3.5 Отмена клоза (кнопка `Отмена клоза` в «управление»)

- Доступна **только Closemod или самому клозеру**, остальным —
  «❌ Отменять клоз может только Closemod или сам клозер.»
- Клоз убирается из реестра, таймер проверки снимается, затем **удаляется категория** — Discord
  удаляет вместе с ней все каналы клоза (чат-клоз, управление, запись, войс).
- Ответ эфемерный: «🚫 Клоз отменён, каналы удаляются.» Шага подтверждения (второго клика) пока нет.

## 4. Что бот пишет в базу данных

Схему создаёт и обновляет **Flyway при старте** (нужны права на DDL):

- `V1__init.sql` — таблицы `players`, `player_roles`, `close`, `close_participant`, `match`,
  `players_match`, `bet_logs`, `points_tx` + индексы;
- `V2__player_steam_name.sql` — колонка `players.steam_name` и индекс по `lower(steam_name)`.

Реально код работает только с `players`:

| Что | Когда | Колонки |
|---|---|---|
| INSERT | первый `/bind` | `discord_id`, `name` (имя в Discord), `steam_id`, `dota_account_id`, `steam_name`, `mmr` (если OpenDota отдал), `win_points = 0` |
| INSERT | первый `/bind_old` | `discord_id`, `name`, `steam_name`; остальные Steam-поля — `null` |
| UPDATE | повторный `/bind` | `steam_id`, `dota_account_id`, `steam_name`, `mmr` (только если OpenDota его отдал — иначе старое значение не затирается), `updated_at = now()` |
| UPDATE | повторный `/bind_old` | `steam_name`, `updated_at = now()` |
| SELECT | `/bind`, `/bind_old`, проверка дубля | по `discord_id` |

Важно:

- `players.steam_id` (BIGINT UNIQUE) — **под SteamID64**, приходит из OpenDota
  в `/bind`. Раньше колонка оставалась пустой, теперь заполняется.
- `players.dota_account_id` — тоже из OpenDota (SteamID32 = account_id).
- `players.mmr` — оценка MMR из OpenDota; при повторном `/bind` **не затирается**,
  если API её не вернул: это защищает значение, записанное ранее.
- `players.rank_tier` — **не пишется**: ранг приходит в API, показывается в ответе
  команды, но в модели `Player` поля нет.
- Vanity-имя Steam (`steamcommunity.com/id/xxx`) в `/bind` не принимается —
  OpenDota не умеет превращать его в `account_id`.
- `steam_id` уникален: один Steam-аккаунт нельзя привязать к двум Discord-профилям
  (конфликт ловится как `SQLException` и показывается игроку общим текстом).
- `discord_id` уникален: повторный bind обновляет существующую строку, второй не создаётся.
- Таблицы клозов/матчей/ставок/очков **созданы, но кодом не используются** — состояние активных
  клозов живёт в памяти процесса (см. раздел 6).
- Пользователю БД нужны: DDL для миграций (`CREATE TABLE`, `ALTER TABLE`, `CREATE INDEX`),
  а также `SELECT`, `INSERT`, `UPDATE`, `DELETE` на `players`.

## 5. Права

### 5.1 Что нужно боту в гильдии (его собственные права)

| Право | Зачем |
|---|---|
| `View Channels` | видеть каналы клоза |
| `Send Messages` | писать сообщения записи и управления |
| `Manage Channels` | создавать категорию/каналы клоза и удалять категорию при отмене |
| `Manage Roles` (Manage Permissions) | расставлять оверрайды прав на каналах клоза |

Плюс при приглашении бота нужен scope `applications.commands` (регистрация слэш-команд).
Привилегированные intents (в т.ч. `GUILD_MEMBERS`) **не запрашиваются**: роли участника для проверки
приходят в payload взаимодействия.

Рекомендуется, чтобы роль бота стояла **выше** роли `Closemod` — иначе Discord может отказать
в правке оверрайдов и/или удалении каналов.

### 5.2 Оверрайды, которые бот сам ставит в каналах клоза

| Канал | @everyone | Closemod | Сам бот |
|---|---|---|---|
| «управление» | 🚫 `View Channel` | ✅ `View Channel`, `Send Messages` | ✅ `View Channel`, `Send Messages`, `Read Message History` |
| «запись» | ✅ `View Channel`, `Read Message History`, `Add Reactions` / 🚫 `Send Messages` | ✅ `Send Messages` | ✅ `View Channel`, `Send Messages`, `Read Message History` |
| «чат-клоз» | не меняются (по умолчанию) | не меняются | не меняются |
| «ожидание» (войс) | не меняются | не меняются | не меняются |

Следствия:

- кнопки управления матчем и клозом видит только `Closemod` (канал «управление» скрыт от всех);
- кнопки «Записаться» / «Отписаться» доступны всем, кто видит «запись» — писать в канал при этом нельзя
  (для кнопок право `Send Messages` не нужно);
- боту выданы явные разрешения в «запись» и «управление», иначе в этих каналах он не смог бы писать.

### 5.3 Роль `Closemod`

- Ищется по имени `Closemod` без учёта регистра. Если роли нет — права не настраиваются,
  в лог пишется «⚠️ Роль Closemod не найдена — права не настроены!», сообщения клоза всё равно создаются.
- Роль нужна, чтобы вызывать `/create_close_dota` и чтобы видеть каналы управления.

## 6. Ограничения текущей версии

- **Состояние клозов только в памяти** (`CloseRegistrations`, `CloseReadinessCheck`): после перезапуска
  бота участники и подтверждения теряются, а кнопки на старых сообщениях отвечают
  «❌ Этот клоз больше не активен.» Таблицы `close` / `close_participant` для этого есть, но не задействованы.
- **Резерв** (11-й и далее) не реализован: приходит «❌ Все 10 мест заняты.» (`close_participant.is_reserve` не используется).
- **Балансировка по MMR** не реализована: команды заполняются по порядку записи
  (в immortal draft состав A выбирает клозер, B собирается из остатка).
- **«Отмена клоза» без подтверждения** — сразу удаляет категорию.
- `/help`, `/info`, `/create_close_cs` — зарегистрированные заглушки без обработчиков.
- Матчи, ставки, `points_tx`, отчёты по клозам/дню — не реализованы.
- `players.rank_tier` не заполняется (ранг показывается в ответе `/bind`, но в модель не занесён).
- Проверка готовности — единственный таймер в боте; он живёт в памяти (шедулер JDA `getGatewayPool()`).

## 7. Как проверить работу

```
./gradlew test          # 76 тестов: CloseMatchTest(29), CloseRegistrationTest(21),
                       # OpenDotaClientTest(16), CloseMessagesTest(7),
                       # SteamBindServiceTest(3, требует Docker)
./gradlew build         # + сборка jar
```

`SteamBindServiceTest` требует живую пустую БД и включается переменными окружения
(без них — пропускается):

```
TEST_DATABASE_URL=jdbc:postgresql://localhost:5432/tournament_test \
TEST_DATABASE_LOGIN=postgres \
TEST_DATABASE_PASSWORD=secret \
./gradlew test
```

Тест сам накатывает миграции Flyway в указанную базу и проверяет создание/обновление игрока
(`/bind`-сценарий). Отчёт: `build/reports/tests/test/index.html`.

## 8. Структура кода (кратко)

```
src/main/java/com/pocketsage/tournament/
├── Main.java                     # точка входа
├── bot/BotLauncher.java          # миграции → JDA, graceful shutdown
├── bot/commands/
│   ├── CommandRegistry.java      # регистрация /help, /info, /create_close_cs
│   ├── SteamBindHandler.java     # /bind: Steam ID → OpenDota → профиль в БД
│   ├── OpenDotaClient.java       # разбор Steam ID и ответ OpenDota
│   ├── SteamBindOldHandler.java  # /bind_old: ручной ввод ника
│   ├── SteamBindService.java     # сохранение профиля (создать/обновить игрока)
│   └── close/
│       ├── DotaCloseHandler.java        # /create_close_dota: роль + модалка
│       ├── DotaCloseService.java        # категория, каналы, права, 2 сообщения
│       ├── CloseRegistration.java       # состояние клоза, слоты, тексты сообщений
│       ├── CloseRegistrations.java      # реестр клозов + кнопки + перерисовка карточки
```
